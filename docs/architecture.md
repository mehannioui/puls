# Pulse — Architecture Decisions

Why we made the calls we did. Read when you're about to revisit one.

---

## 1. River (not Celery, not a custom scheduler) for check scheduling

**Decision:** Use [River](https://riverqueue.com) — Go-native, Postgres-backed job queue —
to schedule + run service checks.

**Why:**
- Already running Postgres; no extra broker (Redis, RabbitMQ) needed.
- Native Go types, no JSON marshaling boilerplate.
- Handles retries, dead-letter, leader election, scheduled jobs out of the box.
- Custom scheduler would need to solve all of the above anyway.

**Tradeoff:** River is younger than Sidekiq/Celery. Acceptable — Postgres durability
covers worst-case failure modes.

---

## 2. Plain Postgres for `check_results` (not TimescaleDB)

**Decision:** Store every check result in a normal table, indexed on
`(service_id, checked_at DESC)`. Aggregate to hourly/daily rollups via a nightly job
once we cross ~10M rows.

**Why:**
- TimescaleDB on Supabase requires extensions + tier-up; not worth it for v1 volume.
- 1k services × check/min × 30 days = 43M rows. Manageable with proper indexing +
  partitioning if needed.
- Aggregation to a `check_results_hourly` table keeps the public status page fast.

**Revisit when:** we cross 5k active services or query latency on the dashboard
exceeds 500ms.

---

## 3. SSE (not WebSockets) for real-time dashboard

**Decision:** Use Server-Sent Events for the live status feed.

**Why:**
- One-way traffic (server → client); WebSockets are overkill.
- Native browser `EventSource` API; no library needed in Nuxt.
- Survives HTTP/2 multiplexing; plays well with Vercel + Fly.io.
- WebSockets would need session affinity, ping/pong, reconnect logic.

**Tradeoff:** SSE doesn't support binary frames. Not needed here.

---

## 4. SSG for public status pages (regenerated on change)

**Decision:** Public status pages (`<slug>.pulse.io`) are statically generated by Nuxt
and revalidated via on-demand ISR when an incident or service status changes.

**Why:**
- Status pages are read-heavy, write-rare. SSG is the natural fit.
- Survives traffic spikes during outages (the moment they're needed most).
- Vercel `revalidatePath` triggered by Go backend on incident events.

**Tradeoff:** Latency between failure and public visibility is the SSG rebuild time
(~10s). Acceptable — we're not promising sub-second public updates.

---

## 5. Wildcard subdomain routing

**Decision:** `*.pulse.io` resolved by Nuxt route middleware. Each tenant gets a
slug; the middleware reads `request.host`, looks up the org, hydrates page data.

**Why:**
- Cleaner than path-based (`/status/acme`) for branding and SEO.
- Vercel supports wildcard domains natively.
- Custom domains (`status.acme.com`) added in v2 with the same pattern.

---

## 6. sqlc (not GORM, not ent)

**Decision:** Write SQL by hand in `db/queries/*.sql`; sqlc generates type-safe Go.

**Why:**
- The SQL we write is the SQL that runs. No ORM magic, no N+1 surprises.
- Compile-time safety for query shape; trivial to debug.
- Encourages writing queries that fit the actual access pattern, not generic CRUD.

---

## 7. Supabase Auth (not Clerk, not Auth0)

**Decision:** Supabase Auth issues JWTs; Go validates them via `SUPABASE_JWT_SECRET`;
RLS policies read `org_id` from JWT claims.

**Why:**
- Already in the stack (Postgres comes from Supabase).
- Free tier covers ~50k MAU; sufficient for v1.
- Native RLS integration — auth and tenancy enforced in one layer.

**Tradeoff:** Vendor lock to Supabase. Migration path exists (export users + reset
passwords), but it's friction.

---

## 8. RLS on every table

**Decision:** Every table has `org_id uuid NOT NULL`. RLS policy:
`org_id = (auth.jwt() ->> 'org_id')::uuid`. The Go service role bypasses RLS — only
the worker uses it, and every insert must set `org_id` explicitly.

**Why:**
- Tenancy at the DB layer means a buggy app query can't leak data.
- Defense in depth; app-level checks are the second line, not the only line.

**Risk:** Forgetting `org_id` in worker inserts. Mitigation: code review checklist +
a sql linter rule (planned).

---

## 9. Modular monolith (not microservices)

**Decision:** Two Go binaries: `cmd/api` (HTTP) and `cmd/worker` (River jobs).
Shared `internal/` packages. One Postgres, one deploy target per binary.

**Why:**
- Solo/small team; coordination overhead of microservices is unjustified.
- Both binaries share the same DB schema and types — splitting them would just add
  serialization at the boundary.
- Can extract a service later if a hotspot emerges.

**Revisit when:** the check engine needs independent scaling (likely after 10k
services), or build/deploy time of one binary blocks the other.
